# progenax website — design document

**Status:** DRAFT — under review
**Author:** Anna Rosen + Claude (brainstorming session, 2026-04-28)
**Tool:** [MyST-MD](https://mystmd.org) (`myst.yml`)
**Location:** `docs/website/`
**Goal:** Single source of truth for progenax — theory, architecture, API, tutorials, history.

---

## 1. Purpose & audience

progenax sits at the intersection of stellar dynamics, turbulent ISM theory,
and differentiable scientific computing. The website is its *one source of
truth*: the place a reader goes for any of "what does this code do," "why
does it do it that way," "what is the physics behind it," and "how do I
use it."

Three audiences, served by overlapping reading paths through one curated
site:

- **Onboarding students** entering the group — typically grad students new
  to differentiable astrophysics, JAX, or N-body initial conditions. They
  need a guided narrative path, executable tutorials, glossary, and
  "minimum viable Plummer sphere" before they need API reference.

- **Future developers** — visiting researchers, collaborators, future-Anna
  six months from now. They need theoretical depth (full derivations),
  architecture rationale ("why protocol-based," "why is `solve_king_profile`
  inside `profiles/`"), API reference, and a development log to find
  *when* a thing was decided and why.

- **The PI (Anna)** — daily reference, fast navigation, accurate citations
  for paper writing, regression-resistant API documentation that survives
  refactors.

Reading paths are not pages, they are *entry points* onto the same content.
A "Get started" landing card walks a student through tutorial → glossary
→ shallow theory; a "Theory & methods" landing card walks a researcher
through full-depth chapters with citations; an "API reference" landing
card jumps straight to autogenerated symbol pages. All three converge on
the same chapter content through cross-links.

## 3. Theory section detail and source-doc mapping

Each theory chapter follows the same template:

1. **Physical motivation** (1-2 paragraphs, no equations) — why this
   model exists, what observable phenomenon it captures.
2. **Mathematical formulation** — the closed-form / ODE / sampling
   procedure, derived (not just quoted). Hidden lemmas in expandable
   admonitions to keep the main flow readable.
3. **Implementation in progenax** — class signatures, key formulas
   linked to source line numbers, gotchas and historical bugs.
4. **Limits and caveats** — domain of validity, known failure modes,
   numerical safety clips.
5. **References** — `{cite}` to the canonical paper(s), at least one
   pedagogical review, and any progenax internal note.

**Source-doc → theory-chapter mapping:**

| Theory chapter | Existing source(s) to absorb | New material to write |
|---|---|---|
| `spatial-profiles/plummer.md` | (none — write fresh; cite Plummer 1911, Aarseth+1974) | Full chapter incl. r_h↔a derivation, scale-radius bug history |
| `spatial-profiles/king.md` | (none) | LIMEPY comparison, ODE solver |
| `spatial-profiles/eff.md` | (none) | EFF profile derivation |
| `velocity-dfs/*` | `dev-methods-guides/jax_native_q_parameter_design.md` (partial — Q discussion only) | Eddington inversion, anisotropy |

## 4. API reference strategy

mystmd does not ship a Sphinx-quality autodoc out of the box. We have
three options:

**Option A — hand-written reference pages.** One MyST page per module
(`30-api/profiles.md`, `30-api/imf.md`, …), each containing a curated
overview plus signatures copied from docstrings. *Rejected:* drifts
from code. The whole point of "single source of truth" is defeated if
the API page contradicts the actual symbol.

**Option B — autogenerate from source via [Griffe](https://mkdocstrings.github.io/griffe/).**
A small build script (`scripts/build_api_reference.py`, ≤200 LOC) walks
the `progenax.*` namespace using Griffe, extracts signatures and
docstrings, and emits one `30-api/<module>.md` MyST file per source
module. Run as a pre-build hook (`myst build` invokes it via a
`prebuild` script in `package.json` or a Makefile target). Same trick
used by `mkdocstrings` and modern equinox docs. Output is regenerated
on every build, so it cannot drift. *Recommended.*

**Option C — bridge to sphinx-autoapi.** Use Sphinx to generate RST
files, convert to MyST, slot into mystmd. *Rejected:* two build systems,
fragile.

**Decision: Option B.** The build script reads `progenax.__all__`,
walks public submodules, and emits MyST pages with: signature, parsed
docstring (numpydoc-formatted), source-link to GitHub line number,
gradient-compatibility flag (parsed from a `:differentiable: yes/no`
docstring tag we'll add to public functions), and a `{cite}` block
when the docstring references a paper.

Symbol pages are *content addressed* (one MyST `(target)=` anchor per
symbol) so that a theory chapter writing `{py:class}\`progenax.PlummerProfile\``
auto-cross-links to the API page.

A single `30-api/full-symbol-index.md` page lists every public export
alphabetically with one-line summary — searchable at a glance.

## 5. Tutorials, executability, citations

**Executability — pre-executed, committed outputs.** Tutorials live as
`.ipynb` files (or `.md` with MyST notebook syntax) under
`00-getting-started/`. They are executed *locally* by the author with
a JAX install, outputs committed to git, and *not* re-executed at
website build time. Rationale:

- A grad student reading the docs should not need a JAX install just
  to render the site.
- CI build time stays fast (mystmd only renders, doesn't execute).
- Notebook outputs become part of the diff — easy to spot if a
  refactor breaks a tutorial.

A simple `make tutorials` target re-executes all notebooks via
`jupyter execute` against the project venv. Author runs it before
committing tutorial changes; it is *not* part of CI (we'd just be
running JAX in CI for nothing).

**Citations — single global `references.bib`.** All papers cited
anywhere in the site live in `docs/website/references.bib`. Cited
inline with `{cite:p}` (parenthetical) or `{cite:t}` (textual). The
`99-bibliography/bibliography.md` page renders the full sorted list
via `{bibliography}`.

Initial seed entries (extracted from existing `core-papers/` PDFs
and the codebase docstring references): Plummer 1911, King 1966,
Elson Fall Freeman 1987, Salpeter 1955, Chabrier 2003, Maschberger
2013, Kroupa 2001, Sana+ 2012, Moe & Di Stefano 2017, Goodwin & Whitworth
2004, Aarseth+ 1974, Baumgardt+ 2008, Sůbr+ 2008, Allison+ 2009,
Marks+ 2012, Jerabkova+ 2018, Federrath & Klessen 2012, Burkhart 2018,
Burkhart 2021, Parmentier & Pasquali 2020, Tan Krumholz McKee 2006,
Kainulainen+ 2014, Hurley Pols Tout 2000.

Cross-refs to ADS / arXiv / DOI use mystmd's first-class link syntax;
`{cite}` resolves to the bibliography page; bibliography entries
themselves link out to ADS.

**Glossary.** `00-getting-started/glossary.md` defines terms once
(virial Q, half-mass radius, freefall-density factor, IMF, mass
segregation, Jacobi radius, …) and other pages auto-link via
`{term}` syntax.

## 6. Migration plan & file-by-file mapping

**Phase A — scaffold (1 commit):**
- Create `docs/website/myst.yml`, `references.bib`, `index.md`,
  empty stubs for the 8 top-level parts, `scripts/build_api_reference.py`.
- Verify `myst build` runs end-to-end on the empty skeleton.

**Phase B — migrate existing material (1-2 commits per chapter):**

| Source | Destination | Action |

| `dev-methods-guides/gravoturbulent_fdf_IC_theory_guide.md` | `10-theory/gravoturbulence/pdf-and-fdf.md` (+ split into pp20.md, bm19.md) | Restructure into 3 chapters |

| `core-papers/progenax-gravoturbulent-fdf-theory-OLD.md` | (delete; superseded) | Add deprecation note in commit |
| `core-papers/progenax_env_imf_implementation_guide.md` | `10-theory/imfs/environment.md` | Move + reformat |
| `core-papers/progenax_mass_segregation_implementation_guide.md` | `10-theory/tidal-and-substructure/mass-segregation.md` | Move + reformat |

| `plans/*.md` | `90-development-log/index.md` (link out only) | Link |
| `PHASE1_COMPLETE.md` | `90-development-log/index.md` (link) | Link |

**Phase C — author new theory chapters** (Plummer, King, EFF, velocity
DFs, classic IMFs, binaries, tidal). One commit per chapter, each
under 800 lines, written with the manuscript-voice skill applied
where helpful.

**Phase D — API reference build script.** One commit. Script under
`scripts/build_api_reference.py`. CI verifies output against committed
snapshot to catch unintended public-API drift.

**Phase E — tutorials.** Three notebooks: `first-plummer-sphere.ipynb`,
`differentiable-ic.ipynb`, `imf-sampling.ipynb`. Pre-executed.

**Phase F — final polish.** Bibliography curation, glossary, landing
page audience cards, cross-link audit, single full `myst build` review.

**Old-doc cleanup policy.** After each migration commit, the source
file is deleted in the *same* commit (not a separate "cleanup" commit).
This keeps the diff legible: "moved X to Y" is one atomic change.
Replacement stub files are *not* left behind — anyone with a stale
link gets a 404 and updates, which is healthier than indefinite
redirect debt. CLAUDE.md and any code docstring references are
updated in the same commit.

## Open questions for sign-off

1. **Executability decision** — pre-executed notebooks committed to
   git, *not* re-executed in CI. (My recommendation; locks unless
   you'd rather have CI run JAX.)

2. **API reference strategy** — Option B: Griffe-based custom build
   script, auto-regenerated on each build. (My recommendation.)

3. **Migration cadence** — single big PR (all phases A-F at once),
   or one PR per phase? My recommendation: **one PR per phase**, so
   each step is reviewable. Phase A scaffolding lands first and
   proves the build works before content lands.

4. **Hosting** — local-only for now (you read it via `myst start`),
   or also publish to GitHub Pages? My recommendation: defer hosting;
   land the content first, hosting is a 30-minute CI job whenever
   you want it public.
